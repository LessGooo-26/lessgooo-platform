# Exploitation du campus local

Voir README.md pour les commandes. Node 22.23 minimum ; SQLite natif. Les intégrations facultatives utilisent OAuth Google et l'API hébergée Notch Pay côté serveur. Les installations sont verrouillées par package-lock.json. Réutilisation des primitives Radix du prototype et de ses dépendances de style ; Zod valide les mutations, tsx lance le serveur de développement et esbuild produit son bundle. Aucun SDK cloud ni dépendance Sites dans le runtime local ; aucune dépendance supplémentaire pour l'extension du campus.

La requête GET /api/health contrôle la lecture de la base. L'API refuse les origines et hôtes non locaux, les méthodes inattendues, les versions périmées et les formulaires trop volumineux. Tous les formats de fichiers sont acceptés jusqu'à 200 Mo, envoyés par blocs de 4 Mo et téléchargés comme pièces jointes application/octet-stream avec nosniff. Les téléchargements utilisent une pipeline avec gestion de pression et interruption. L'ancien endpoint multipart demeure limité à 5 Mo. Les transferts partiels expirent après 24 h ; les fichiers terminés ne sont pas supprimés automatiquement. Les vues de démo sont filtrées côté serveur. Aucune authentification multiutilisateur n'est simulée comme une sécurité réelle.

`workspace-store.ts` ajoute tables de notes, inscriptions, candidatures, blocs binaires et file Drive, dans la même base sauvegardée. Les révisions protègent les notes des écritures concurrentes. La migration du catalogue est additive et normalise les identifiants du premier brouillon sans perdre les devoirs ni écraser un contenu modifié.

`integrations.ts` applique un state OAuth à durée limitée, PKCE, un cookie HttpOnly et la vérification de l'email attendu. L'exception cross-site est limitée au callback OAuth GET, validé par state et cookie. Les secrets stockés et le refresh token sont chiffrés AES-GCM avec une clé locale séparée ; les configurations ne sont jamais renvoyées. La sauvegarde inclut une copie privée de cette clé lorsqu'elle existe. Un environnement de production devra remplacer le sélecteur de démo par une vraie authentification avant d'exposer les réglages.

Les fichiers Drive utilisent un transfert reprenable ; leur identifiant distant est conservé pour mettre à jour la même copie lors d'une nouvelle correction. La file garde ses erreurs et n'annonce un succès qu'après confirmation distante. Les traitements sont sérialisés ; une modification survenue pendant un transfert reste en attente du passage suivant. Les transactions Notch Pay ne sont confirmées qu'après interrogation serveur et correspondance de tous les champs attendus. Aucun webhook ni secret n'est exposé sur GitHub Pages.

Le connecteur Notch Pay accepte le format documenté `id/reference` et le format observé en sandbox `reference/merchant_reference`. Dans ce dernier cas, la référence prestataire est conservée séparément et utilisée pour la lecture de la transaction. Le marqueur sandbox accepte uniquement un booléen ou 0/1 et doit correspondre à la configuration locale lorsqu'il est présent. La création d'un lien ne vaut jamais confirmation de paiement.

La commande backup utilise l'API SQLite, compatible WAL, et inclut toutes les pièces jointes. Le test de restauration ouvre la copie dans une base distincte et vérifie les octets d'une pièce jointe. Les tests ne touchent jamais la base utilisateur : ils utilisent des dossiers temporaires isolés ou :memory:.

Le Dockerfile comprend les validations avant compilation et un runtime non-root. Compose limite le port hôte à 127.0.0.1 et conserve un volume. Ne pas configurer CAMPUS_CONTAINER=1 en dehors du conteneur. Le volume et la base ne doivent pas être publiés.

Les workflows existants conservent leurs validations. CI est étendue aux branches codex. Pages utilise son sous-chemin historique, avec PAGES_BUILD=1, et ne publie que dist/. Le serveur compilé est dans dist-server/ et n'est jamais envoyé à Pages.

Depuis le 17 septembre 2026, les images JPG/PNG/GIF/WebP et conteneurs MP4/WebM/Ogg reconnus par leur signature peuvent être affichés en ligne. Les autres contenus, notamment SVG et HTML, restent des pièces jointes. GET prend en charge une plage HTTP unique et HEAD les métadonnées. Les blocs SQLite sont découpés en flux sans recharger le fichier complet. Le paramètre persona des lectures natives vidéo/image conserve le filtrage de la démonstration ; il ne constitue pas une authentification. Les mutations continuent à utiliser l’en-tête de vue.

La migration média ajoute gallery et preview sans supprimer les fichiers terminés. Les profils et galeries utilisent workspace_items. Les transferts annulés ne suppriment que leurs propres blocs incomplets. Les traductions sont locales et le choix EN/FR est mémorisé ; aucun contenu personnel n’est envoyé à un service de traduction.
